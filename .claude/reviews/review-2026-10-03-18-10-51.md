### 4. WorkerBridge 跨域加载、virtualFS 代理、Token 协调

**审查文件**:
- `packages/component/src/worker-bridge.ts`

**发现的问题**:

#### 问题 4.1: 跨域 fetch 缓存策略过于激进 (警告)
- **文件**: `worker-bridge.ts:112` (原代码)
- **问题**: 使用 `cache: 'no-store'` 导致每次页面加载都重新下载 SharedWorker 脚本
- **严重程度**: 警告
- **修复状态**: ✅ 已修复
- **修复说明**: 改为 `cache: 'default'`。生产环境 CDN 脚本使用 content-hash，开发环境 URL 每次 HMR 都不同，`default` 策略在两种场景下都合理。

#### 问题 4.2: 每次 yield 创建新 MessageChannel (警告)
- **文件**: `worker-bridge.ts:280-290` (原代码)
- **问题**: `_yieldToMain()` 每次调用都 `new MessageChannel()`，在 catch-up 循环中会产生大量短生命周期对象
- **严重程度**: 警告
- **修复状态**: ✅ 已修复
- **修复说明**: 改为共享 `_yieldChannel` 实例，使用队列管理 resolve 回调。同时在 `destroy()` 中添加 channel 清理。

#### 问题 4.3: Token 协调的 Promise 缓存 Bug (已在先前修复)
- **说明**: 此问题已在之前的审查中修复（见 memory: `workerbridge-token-caching-bug.md`）

**总体评价**: ★★★★☆ - 已修复关键问题

### 5. Ready 信号机制 (Promise + CustomEvent dual-channel)

**审查文件**:
- `packages/component/src/core/ready.ts`
- `packages/component/src/components/rtc-agent/rtc-agent.ts`

**发现的问题**:

#### 问题 5.1: rtc-agent-ready 事件在 React StrictMode 下重复派发 (严重)
- **文件**: `rtc-agent.ts:1462-1468`
- **问题**: React StrictMode 会 mount → unmount → remount 组件，导致 `firstUpdated()` 执行两次，`rtc-agent-ready` 事件被派发两次
- **严重程度**: 严重
- **修复状态**: ✅ 已修复
- **修复说明**: 添加 `_readyDispatched` 标志位，确保事件只派发一次：
  ```typescript
  if (!this._readyDispatched) {
      this._readyDispatched = true;
      this.dispatchEvent(new CustomEvent<void>('rtc-agent-ready', {...}));
  }
  ```

**总体评价**: ★★★★☆ - 已修复关键问题

### 9. ScriptEngine 沙箱安全

**审查文件**:
- `packages/persistence/src/script-engine.ts`

**发现的问题**:

#### 问题 9.1: 紧密循环 DoS 潜在风险 (建议)
- **文件**: `script-engine.ts:540-600`
- **问题**: 虽然设置了执行超时，但同步的紧密循环（如 `while(true){}`）在单个事件循环中可能阻塞主线程
- **严重程度**: 建议
- **修复状态**: ❌ 未修复（设计权衡）
- **说明**: 当前使用 `setTimeout` 实现超时，对于同步代码的紧密循环无法中断。完整的解决方案需要使用 Web Worker 执行脚本或 Babel 插件插入循环计数检查。考虑到当前使用场景（LLM 生成的数据处理脚本），风险可控。建议在文档中明确此限制。

**观察**:
- BLOCKED_GLOBALS 和 BLOCKED_MEMBER_PROPERTIES 列表全面
- Babel AST 变换在编译期阻止危险访问
- `new Function()` + `"use strict"` + `fn.call(undefined)` 防止 `this` 逃逸

**总体评价**: ★★★★☆ - 安全性良好，有已知限制

### 10. 组件树层次结构与 Context 消费关系

**审查文件**:
- `packages/component/src/components/rtc-agent/rtc-agent.ts`
- `packages/component/src/contexts/*.ts` (17 个 context 文件)

**发现的问题**:

#### 问题 10.1: updated() 中同步所有 17 个 Context Provider (建议)
- **文件**: `rtc-agent.ts:1345-1376`
- **问题**: 每次 `updated()` 都同步所有 17 个 provider，即使只有 1-2 个 controller 状态发生变化
- **严重程度**: 建议
- **修复状态**: ❌ 未修复（性能优化机会）
- **说明**: 当前设计使用 `updateComplete.then()` 延迟同步以避免 "change-in-update" 警告，这是正确的。但全量同步在大规模状态变更时可能产生不必要的 re-render。优化方案：使用 Reactive Controller 的 `hostUpdated()` 钩子，或在每个 controller 内部直接调用 `provider.setValue()`。但这需要较大的重构，当前规模下影响有限。

#### 问题 10.2: workerBridge 非空断言 (严重)
- **文件**: `rtc-agent.ts:_loadScenarios()` 和 `_regenerateDocsAfterRegistrySet()`
- **问题**: 使用 `this._persistence.workerBridge!` 非空断言，如果 invariants 被破坏会导致崩溃
- **严重程度**: 严重
- **修复状态**: ✅ 已修复
- **修复说明**: 改为安全的 null 检查：
  ```typescript
  const bridge = this._persistence.workerBridge;
  if (!bridge) {
      log.warn('WorkerBridge not available, skipping scenario load');
      return;
  }
  await bridge.core.batchWriteFiles(files, deletePaths);
  ```

#### 问题 10.3: connection-setup.ts 中 dead variable (警告)
- **文件**: `connection-setup.ts:217-222` (原代码)
- **问题**: `setupConnectionListener()` 中的 `currentState` 变量在闭包中被赋值但从未被读取
- **严重程度**: 警告
- **修复状态**: ✅ 已修复
- **修复说明**: 移除 dead variable，简化函数逻辑。

#### 问题 10.4: connection-setup.ts 中 AskUserDialogFn 类型断言过于复杂 (警告)
- **文件**: `connection-setup.ts:182-184`
- **问题**: 使用 `as unknown as AskUserDialogFn` 双重类型断言
- **严重程度**: 警告
- **修复状态**: ✅ 已修复
- **修复说明**: 简化为 `as ReturnType<AskUserDialogFn>`，更清晰且类型安全。

**总体评价**: ★★★★☆ - 已修复关键问题，有优化空间
